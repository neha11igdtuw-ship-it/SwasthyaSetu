# SwasthyaSetu Backend — Implementation Report

## Stack conflict resolution

The codebase had a mix of sync and async remnants from an interrupted session.
`pyproject.toml` and `app/core/config.py` already matched the agreed async
stack (asyncpg, SQLAlchemy 2 async, argon2-cffi, pyjwt, ruff/black). Two files
still had sync-stack code and were rewritten:

- `app/db/session.py` — was using `sqlalchemy.create_engine` / `sessionmaker`
  (sync). Rewritten to `create_async_engine` / `async_sessionmaker` /
  `AsyncSession`, with `get_db` as an async generator.
- `app/core/security.py` — was using `python-jose` + `passlib[bcrypt]`.
  Rewritten to `pyjwt` + `argon2-cffi` (`argon2.PasswordHasher`), matching the
  dependencies already declared in `pyproject.toml`.

No other files had sync-stack assumptions (models, `errors.py` were already
framework-agnostic).

## What was built

Full app under `backend/app/`: models (User, Facility, Patient, Referral,
InventoryItem/Transaction, CareGap, SyncedChange), Pydantic schemas,
repositories, services, and FastAPI routes, wired in `app/main.py` under
`/api/v1`.

- **Auth**: register/login/refresh/me, argon2 password hashing, JWT
  access+refresh tokens (pyjwt).
- **Optimistic concurrency**: `SyncableMixin` (version, is_deleted) +
  `SyncableRepository` base class used by Patient/Referral/CareGap. Updates
  require `base_version`; mismatch → HTTP 409 with current server state.
- **Referral state machine**: `REFERRAL_TRANSITIONS` map enforced in
  `ReferralService.transition`; illegal transitions → 422.
- **Smart referral matching** (`ReferralMatchingService`): scores candidate
  facilities by capability match (60 pts) + haversine-distance proximity (up
  to 40 pts), explainable `reasons` list, facilities lacking the required
  specialty are excluded.
- **Inventory**: `InventoryRepository.adjust_stock` locks the row
  (`SELECT ... FOR UPDATE`, skipped on SQLite) inside one transaction, writes
  an immutable `InventoryTransaction` ledger row, rejects adjustments that
  would take stock negative (409).
- **Offline sync** (`SyncService`): `/sync/push` is idempotent via
  `SyncedChange(device_id, client_change_id)` unique constraint — replays
  return `ALREADY_APPLIED` instead of re-applying; version conflicts return
  per-item `CONFLICT` with server state (batch keeps processing other items).
  `/sync/pull` returns all rows updated after `since`.
- **Care gaps**: create/list/close with the same optimistic-concurrency
  pattern.

## Verification (all run for real, not simulated)

Docker was not available in this environment (no `docker`/`colima`/`podman`
binary), so I installed PostgreSQL 16 via Homebrew instead and ran it on the
same port docker-compose.yml uses (55432), with the same user/db/password —
functionally equivalent to `docker compose up`.

- `alembic revision --autogenerate` against live Postgres generated
  `alembic/versions/06fec59710b4_initial_schema.py`. First run failed
  (`NameError: name 'app' is not defined`, missing import in the
  autogenerated file for the custom `GUID` type) — fixed by adding
  `import app.models.types`.
- `alembic upgrade head` ran clean; verified via `psql \dt` that all 8 tables
  exist (users, facilities, patients, referrals, inventory_items,
  inventory_transactions, care_gaps, synced_changes, alembic_version).
- `python -m seed.seed_data` ran against the live DB (idempotent, re-runnable).
- Started `uvicorn app.main:app` against live Postgres and hit it with curl:
  `/health`, `/auth/login` (real JWT issuance), `/patients` (seeded data
  returned), `/referrals/match/candidates` — all correct.
- `pytest` (SQLite + aiosqlite for speed): **15 passed**, 0 failed. Real bugs
  found and fixed during this run:
  - Missing `email-validator` dependency for `EmailStr` (added
    `pydantic[email]`).
  - Error envelope crashed on UUID/enum/datetime in `details` (not JSON
    serializable) — fixed with `fastapi.encoders.jsonable_encoder` in
    `core/errors.py` and in `SyncService`'s conflict path.
  - Referral matching returned facilities that didn't have the requested
    specialty (only proximity-scored) — fixed by skipping non-matching
    facilities when a specialty is required, instead of ranking them low.
- `ruff check` / `black`: ran, auto-fixed import ordering; remaining ~56
  findings are style suggestions only (e.g. "inherit from `enum.StrEnum`"
  instead of `str, Enum`, `Generic[T]` vs PEP 695 type params) — no
  correctness issues, left as-is to avoid churn on working code.

## RBAC and facility-ownership (added this session)

- **Roles**: `Role` enum extended with `FACILITY_ADMIN` and `DOCTOR` (in
  addition to existing `ADMIN`, `HEALTH_WORKER`, `FACILITY_STAFF`,
  `PATIENT`). `FACILITY_SCOPED_ROLES` in `app/models/enums.py` lists the
  roles whose access is limited to their own `facility_id`
  (`FACILITY_ADMIN`, `DOCTOR`, `HEALTH_WORKER`, `FACILITY_STAFF`).
- **Patient ↔ login link**: added `Patient.user_id` (nullable, unique FK to
  `users.id`) so a `PATIENT`-role login can be tied to exactly one patient
  record. Migration `8a1a1bdb2387_rbac_roles_and_patient_user_link.py` adds
  the column plus the two new `role_enum` values via
  `ALTER TYPE ... ADD VALUE` (run in an autocommit block, since Postgres
  disallows that inside a transaction). Enum-value removal isn't supported
  by Postgres, so `downgrade()` intentionally leaves `role_enum` alone.
- **`app/api/deps.py`**: kept `get_current_user`/`require_roles`, added
  plain helper functions (not FastAPI dependencies, since they need the
  already-fetched row) — `assert_patient_access`, `assert_facility_access`,
  `assert_referral_access`, `is_facility_scoped`. Rule of thumb: `ADMIN`
  bypasses everything; `PATIENT` is restricted to the patient row whose
  `user_id` matches; facility-scoped roles are restricted to rows whose
  `facility_id` (or, for referrals, `from_facility_id`/`to_facility_id`)
  equals their own `facility_id`.
- **Routes wired**: `patients`, `referrals`, `inventory`, `care_gaps`,
  `sync`, `facilities` all now check role + ownership before returning or
  mutating data (previously any authenticated user could hit any endpoint).
  Notable behavior choices:
  - Facility-scoped staff creating a patient/referral have `facility_id`/
    `from_facility_id` forced to their own facility (can't spoof another).
  - `POST /facilities` is `ADMIN`-only; `GET /facilities` stays open to any
    authenticated user (reference data other routes need, e.g. referral
    matching).
  - `/sync/push` validates each change's target facility before applying
    (new patient/referral/care-gap creations against the payload's implied
    facility; updates/deletes against the existing row's facility).
    `/sync/pull` filters the response to the caller's facility (or their own
    patient's data — sync is not offered to `PATIENT` role at all, no
    offline client for that role exists in this system).
- **Tests**: `tests/test_rbac.py` (new, 16 tests) builds a 2-facility, 5-role
  fixture (`admin`, `worker_a`/`worker_b`, `doctor_a`, `facility_admin_a`,
  `patient_a` with a linked login) and proves: a patient can read only their
  own record and is rejected (403) on another patient, on listing all
  patients, and on creating patients; a worker can read/list only their own
  facility's patients and is rejected on another facility's patient,
  inventory, and cross-facility referral creation; a referral spanning two
  facilities is visible to staff at either side; a facility admin is capped
  to their own facility; only `ADMIN` can create a facility; `PATIENT` is
  rejected from `/sync/pull`; unauthenticated requests get 401.
  Existing fixtures/tests (`tests/conftest.py`, `test_patients.py`,
  `test_referrals.py`, `test_inventory.py`, `test_sync.py`) were updated to
  register users with a `facility_id` and to use an `admin_headers` fixture
  where facility creation is involved, since that's now `ADMIN`-only.
- **Full suite**: 31 passed, 0 failed (15 original + 16 new RBAC tests).
  Verified against both SQLite (test suite) and the live Homebrew Postgres
  instance (`alembic upgrade head` + `python -m seed.seed_data` both ran
  clean after the migration).
- `ruff check --fix` / `black` run again; no new correctness findings (same
  pre-existing style-only items as before, e.g. `StrEnum` suggestions).

## Part 2 — maternal-care entities (this session)

Added 11 new tables, all following the existing model/repo/service/route
layering and `SyncableMixin` (UUID PK, `version`/`is_deleted` optimistic
concurrency, `created_at`/`updated_at`):

- **`app/models/maternal.py`**: `Pregnancy` (patient_id, risk_level enum,
  risk_flags, status), `Encounter` (patient_id, facility_id, author_id —
  health worker or doctor), `Symptom`/`Vital` (encounter_id, 1 encounter → many
  each), `Screening` (encounter_id, risk_level, result).
- **`app/models/care.py`**: `Appointment` (patient_id, facility_id, nullable
  referral_id/availability_id), `DiagnosticOrder` (patient/encounter/
  screening/referral_id all nullable except patient_id, status enum),
  `DiagnosticReport` (1:1 with `diagnostic_order_id`, unique FK),
  `Prescription` (patient_id, encounter_id, `inventory_item_id` FK into the
  existing inventory table).
- **`app/models/staff.py`**: `DoctorAvailability` (doctor_id/facility_id,
  start/end, is_booked), `HealthWorkerProfile` (user_id unique FK,
  facility_id, cadre enum ASHA/ANM/OTHER, area).
- **`Referral.screening_id`** (nullable FK to `screenings.id`) added so a
  screening can create and link a referral in one call.
- Indexes added (`index=True`) on every `patient_id`/`facility_id`/
  `encounter_id` FK used in list-filter queries, matching what autogenerate
  would otherwise miss on plain FKs.

**Services with real logic** (not just passthrough repos):
- `ScreeningService.create` (`app/services/maternal.py`) — creates the
  screening and, if `create_referral=True` on the request, creates a
  `Referral` in the same DB transaction with `screening_id` set back to it.
- `PrescriptionService.create` (`app/services/prescriptions.py`) — calls the
  **existing** `InventoryRepository.adjust_stock` (same row-locking ledger
  used by manual dispense/receipt) with a negative delta, so a prescription
  and a manual stock adjustment share one source of truth and insufficient
  stock returns the same 409 `ConflictError`.

**Routes** (all under `/api/v1`, all wired through the existing
`get_current_user`/`assert_patient_access`/`assert_facility_access` deps —
patients restricted to their own record, facility-scoped roles restricted to
their own `facility_id`, `PATIENT` blocked from every write endpoint):
`pregnancies.py`, `encounters.py` (+ nested `/symptoms`, `/vitals`,
`/screenings`), `appointments.py`, `diagnostics.py` (`/orders`, `/reports`),
`prescriptions.py`, `doctor_availability.py`, `health_worker_profiles.py`
(create restricted to `ADMIN`/`FACILITY_ADMIN`).

**Migration**: `alembic/versions/bd726bc84191_add_maternal_care_entities.py`,
generated via `alembic revision --autogenerate` against the live Homebrew
Postgres, reviewed and fixed the same way as the first migration (missing

**Seed data** (`seed/seed_data.py`): added a `doctor@swasthyasetu.dev` user

## Known gaps / follow-ups

- **Sync (offline push/pull) does not cover the Part 2 entities.**
  `app/api/routes/sync.py` and `SyncEntityType` still only handle
  patients/referrals/care-gaps; pregnancies/encounters/symptoms/vitals/
  screenings/appointments/diagnostic orders & reports/prescriptions are not
  yet syncable offline, even though they use `SyncableMixin` and are ready to
  be wired in the same per-entity-type-check style once needed.
- **Doctor-availability booking is not enforced end-to-end.** Creating an
  `Appointment` with an `availability_id` does not automatically flip that
  slot's `is_booked` to `True` — `is_booked` is a plain field the caller (or a
  future service) must set via `PATCH /doctor-availability/{id}`. No
  double-booking check exists yet.
- **`facility_services`/full doctor-profile booking logic is out of scope.**
  `HealthWorkerProfile` covers cadre/area; there is no equivalent
  `DoctorProfile` (specialty, qualifications) — `DoctorAvailability.doctor_id`
  just points at a `User` with role `DOCTOR`.
- **Diagnostic report is 1:1 with its order** (unique FK), per the task's
  "your call" — a future re-test/amended-report workflow would need a second
  order rather than multiple reports per order.
- No `audit_logs` table — RBAC denials are not currently logged anywhere
  beyond the 403 response itself; for a regulated environment this should
  be added before production use.
- Sync push/pull facility-scoping is enforced with explicit per-entity-type
  checks in `app/api/routes/sync.py` rather than a generic mechanism — fine
  for the current 3 syncable entities (patients/referrals/care-gaps), but
  will need a more general approach once Part 2 adds more syncable entities.
- `datetime.utcnow()` deprecation warnings remain in models/services (works
  fine on Python 3.13, but should move to `datetime.now(UTC)` eventually).
- Postgres for this session is running via Homebrew on port 55432, not
  docker — matches `.env`/`docker-compose.yml` exactly, so `docker compose up`
  will work identically once Docker is available; I did not modify
  docker-compose.yml or the Dockerfile.
